# The countdown waits for the renderer to signal it is ready

The Winner and the Race plan are still drawn the instant `start`/`playAgain` is called (ADR-0001, unchanged): nothing about fairness or timing moves. What changes is that the countdown's own clock does not start immediately after that draw. `PickerSession` gains a `preparing` phase between `input`/`result` and `countdown`: the active renderer (3D or 2D) does whatever one-off work it needs — compiling shaders and drawing an off-screen frame for 3D, nothing for 2D — and calls `stageReady(now)` when it can show something immediately. Only then does the countdown clock (`startedAt`) begin.

This replaces an earlier approach (pre-warming the 3D scene while the Roster screen was still open, `3f3cb2c`–`643f696`) that kept a live WebGL context and a warmed renderer for the entire time names were being typed, to avoid ever showing a "preparing" state. That traded a permanent GPU/battery cost, and two context-lifecycle bugs (a failed warm-up wedging the renderer; R3F's own teardown looking like a real context loss), for skipping a loading message that already existed for the slow-network case. Waiting for the renderer to be ready is a smaller mechanism: one phase, one callback, and no work happens before the user has committed to a Race.

A renderer only ever picks *when* the countdown clock starts — never the Winner, the plan, or the Race Duration — so this does not weaken the neutrality ADR-0002 describes for `laneProgress(now)`. If nothing signals readiness within a fixed timeout, the stage falls back to the 2D renderer for that Race (`stageReady` is then called by the fallback) and reports the same Winner and timing.
